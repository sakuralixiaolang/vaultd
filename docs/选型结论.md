# 阶段 0：开源方案检索与选型结论

> 数据抓取时间：2026-11-22（star / 最近提交 / License / Release 均为当时 API 返回值，会变动）。
> 本文档刻意不含目标云盘品牌名、真实域名、任何凭据；仓库内也不应出现。

---

## 1. 一句话结论

**加密格式与加解密全部交给 rclone（MIT）的 `crypt` 格式，自己不自创格式、不手写密码学；OpenList 只当"密文传输层"，不参与加密；真正要自己补的只有 5 层：本地 Range 网关、相册索引/缩略图 sidecar、上传队列与重试分类、设备绑定密钥引导、UI。**

最大好处：**格式从一开始就是最终格式**。阶段 3 去掉 OpenList 只换传输层，云端已有数据不用重传、不用迁移。

## 2. 关键事实核对（先钉死"能不能用"，再谈选型）

### 2.1 rclone crypt 的文件格式：原生就是分块 AEAD

官方格式说明（`docs/content/crypt.md`）原文要点：

- 文件结构 = **32 字节头**（8 字节魔数 `RCLONE\0\0` + 24 字节 nonce）+ **每块 64 KiB 的块序列**。
- 每块 = **16 字节 Poly1305 认证标签 + 1~65536 字节 XSalsa20 密文**；nonce 每块递增，"each nonce is unique for each block written"。
- 即：**每块独立 nonce、独立 tag** —— 正好满足"分块 AEAD、禁止整文件单 tag"，且不是我们发明的。
- 文件名加密：PKCS#7 补齐到 16 字节 → **AES-256-EME**（宽块模式）→ base32 小写输出；目录名可同法加密。
- KDF：**scrypt(N=16384, r=8, p=1)** 派生 32+32+16 字节（数据密钥 / 文件名密钥 / 文件名 IV）。
- 明确**不加密**：文件长度（16 字节精度）、修改时间。

→ 结论：格式这一层没有任何理由自研。rclone 这个格式已被大量用户长期使用，且**天然可随机读**（块索引由 offset 直接推导，seek 到任意 64 KiB 边界都能独立解密）。

### 2.2 "块索引写进加密 sidecar"这条要求，用 rclone 格式时不需要

rclone 的块索引是**隐式**的（`chunk_index = offset / 65536`），不需要也不应该再造索引 sidecar。真正需要 sidecar 的是**相册索引**（缩略图清单、拍摄时间、宽高、原图映射）——那是应用层的事，和密码学无关，过一遍 crypt 上传即可。

### 2.3 rclone chunker：分片 / 大文件 / 片级断点

- 默认分片 2 GiB，命名 `*.rclone_chunk.###`，另有一个与原文件同名的 **JSON 元数据对象**（`ver/size/nchunks/md5/txn`）。
- 依赖被包裹端支持**服务端 move/rename**，否则直接拒绝工作。
- 与 crypt 叠加时基名可用长度上限 ~119 字符（够用）。
- 分片内的失败只能整片重传 —— **断点粒度 = 分片大小**。

### 2.4 OpenList 的 crypt 驱动 = 直接 import 了 rclone 的 crypt 包

`drivers/crypt/driver.go` 里：

- `rcCrypt "github.com/rclone/rclone/backend/crypt"`，用 `rcCrypt.NewCipher(config)` 建密码器 → **与 rclone 完全同格式**。
- `Link()` 里已实现 `stream.RangeReaderFunc` + `cipher.DecryptDataSeek(...)`，即"带 Range 的流式解密"是现成跑通过的。
- 但它要求底层 Link 提供 `RangeReader`，否则报 `the remote storage driver need to be enhanced to support encryption` —— 这正对应"必须开 Web 代理，否则只有 302 直链"。

→ 这个驱动**非常有参考价值**（是"Range 解密"最好的实现范本），但**不建议当架构基座**（见 4.3）。

### 2.5 OpenList 的 WebDAV 服务端

`server/webdav/*` 是 `x/net/webdav` 的 fork，注册了 `PROPFIND/MKCOL/LOCK/UNLOCK/PROPPATCH/COPY/MOVE`，GET 走标准 `http.ServeContent` 语义（206 / Content-Range）。**但 206 的前提是拿到的句柄可 Seek**，也就是底层 driver 得给 `RangeReader`。

→ **这是整个项目最大的单点风险，阶段 1 第一件事就要 `curl -r` 实测**（见第 7 节），不要默认成立。

## 3. 选型矩阵：到底"能直接复用"什么，"要补哪一层"

| 层 | 直接复用 | 要补什么 | 备注 |
|---|---|---|---|
| 加密格式 / AEAD / KDF | rclone crypt（XSalsa20-Poly1305、AES-EME、scrypt） | **零** | 禁止自研 |
| 文件名 & 目录名加密 | rclone crypt `standard` + `directory_name_encryption=true` | 零 | 确定性加密，见 6.1 |
| 大文件分片 | rclone chunker | 分片大小/命名策略 | 依赖 MOVE |
| WebDAV 客户端 | rclone `webdav` backend（重试、超时、限速、传导 Range） | 配置参数 | 已成熟 |
| Range 解密播放 | rclone crypt 的可 Seek 语义 | **本地 Range 网关（206/416 + token 鉴权 + 只绑 127.0.0.1）** | 唯一必须自写的协议层 |
| 上传 | rclone `Put` 流式 + chunker | **上传队列：失败分类重试（423 / 超时 / 5xx / 网络）、并发与限速** | 片级断点 |
| 相册墙 | 无成熟项目可抄 | **索引 + 缩略图 sidecar（本地生成 → 过 crypt 上传）** | 不涉及密码学 |
| 缩略图生成 | FFmpeg（视频抽帧）、libvips/sharp（图片压缩） | 尺寸/质量策略、并发 | — |
| 播放器 | HTML5 `<video>` 原生 Range | 不用 MSE、不用加密播放器 | 解密在网关完成 |
| 传输（MVP） | OpenList WebDAV | 开 Web 代理、授权续期、超时参数 | 阶段 3 替换 |
| 阶段 3 内置驱动 | 某云盘 CLI（Rust，MIT）行为参考 | 自己写 driver | 不抄 AGPL 代码 |

**"只需要补一层"的准确表述**：加密/格式/分片/WebDAV/播放器都有成熟实现，**真正要自己写并且必须写对的，只有"本地 Range 网关"这一层**（约百来行：解析 Range → 组 `RangeOption` → `obj.Open()` → 206 响应头 + 流式 body）。其余是编排与产品层。

## 4. 架构方案

### 4.1 推荐分层

```
[ WebView2 / 浏览器 ]  <video src="http://127.0.0.1:PORT/s/<token>/media/...">
        | HTTP，支持 Range，只绑 127.0.0.1
+-------v--------------------------------------------+
| Go 核心（单进程，后续可 gomobile 复用到移动端）        |
|  1 Range 网关：206/416、token 校验、Origin 校验      |
|  2 列表/目录：fs.List（返回解密名与真实大小）          |
|  3 上传队列：流式 Put + chunker + 失败分类重试        |
|  4 相册：本地抽帧/压缩 -> sidecar 加密上传 -> 列表解密 |
|  5 密钥引导：首启生成随机主密钥 -> 本地 config        |
+-------v--------------------------------------------+
        | rclone fs（进程内，或临时用子进程）
        | chunker -> crypt -> webdav
+-------v--------------------------------------------+
| OpenList WebDAV（独立进程，Web 代理 ON）              |
+-------v--------------------------------------------+
        | HTTPS，只有密文
[ 运营商个人云盘 ]
```

**为什么 chunker 在外、crypt 在内（`chunker:crypt:webdav`）**：每个分片的文件名整体被 crypt 加密，云端看到纯 base32 乱码，连 `.rclone_chunk` 这种结构性后缀都不暴露，也没有工具指纹。反向叠加（`crypt:chunker`）会在密文名后挂 `.rclone_chunk.001`，泄露"这是分片、这是某个工具的产物"。

**为什么自建网关，而不是直接 `rclone serve webdav`**：`<video>` 发不了自定义鉴权头；`serve webdav` 的 VFS 默认 `--vfs-read-chunk-size=128Mi`，一次跳转会预读 128 MB，4 GB 视频拖到 90% 白下 128 MB。自建网关可把 Range 透传成一次精确的 `RangeOption`。

### 4.2 三种落地形态（按阶段用）

| 形态 | 做法 | 用在哪 | 代价 |
|---|---|---|---|
| A. 子进程 `rclone serve webdav` | 3 条命令级链路验证 | **阶段 0.5 / 阶段 1 摸底**，10 分钟证明 206 成立 | 鉴权、预读不可控 |
| B. Go 内嵌 rclone `fs` + 自建网关 | `fs.NewFs("chunker:crypt:webdav...")` -> `obj.Open(&fs.RangeOption{...})` | **阶段 1~3 正式形态** | 编译体积、升级跟随 rclone |
| C. 阶段 3 自带驱动 | 只把底层 `webdav` 换成平台 API，crypt/chunker 不动 | 去掉 OpenList 常驻 | 需自写 driver（参考 MIT 那个 CLI 的行为，不抄 AGPL 代码） |

B 能成立有硬证据：OpenList 自己就在 import `github.com/rclone/rclone/backend/crypt` 当库用。

### 4.3 为什么不直接用 OpenList 的 crypt 驱动（省掉自写网关）

它确实能让"零代码"跑通 Range 解密，但有三个致命点：

1. **加密层绑在上游代理**：阶段 3 去掉 OpenList 时，等于把 crypt 一起搬走，格式/密钥/迁移全部重来。
2. **AGPL-3.0**：把它的代码并进自有客户端会传染；即便只是"用"，也意味着 App 离开 OpenList 就不能工作。
3. 它要求底层 driver 有 `RangeReader` —— 问题只是被推后，没有被解决。

正确用法：**当"Range 解密"的行为范本 + 阶段 0.5 的免费可行性测试**（见 7.1）。

## 6. 必须提前接受的妥协（别到验收才发现）

**6.1 确定性文件名的泄漏面**
AES-EME 是确定性加密：**同名文件 -> 同密文名**；云端能看出"两个目录里有同名文件"、"目录树形状"、"有多少文件"。这是该格式为"能在对象存储上按名查找"付出的代价，没有开关。可接受（拿不到内容），但要写进 README。

**6.2 大小与时间泄漏**
文件长度只差 16 字节精度、mtime 不加密 -> 云端知道你存了多大的东西、什么时候传的。缩略图同理（小文件尺寸会暴露）。

**6.3 断点粒度**
rclone 分片内上传不可续传，重试 = 整片重来。真正"细粒度断点"要等阶段 3 自带驱动、直接调平台的分片上传 API（也是那个 MIT CLI 的做法）。MVP 阶段别承诺"任意位置续传"。

**6.4 chunker 强依赖 MOVE**
被包裹端不支持 rename 就直接罢工。OpenList WebDAV 注册了 MOVE，但目标驱动是否可靠要实测；兜底是 `chunk_size` 调大到不触发分片（或 `transactions=norename`，实验性，不建议生产）。

**6.5 AGPL 边界**
OpenList 独立进程运行、不改它 -> 我方代码不受 AGPL 约束；但一旦把它的目标云盘驱动代码抄进客户端，客户端就变 AGPL。阶段 3 请"看行为、不抄代码"。

**6.6 移动端不要重写密码学**
阶段 4 走"App 内 localhost 代理 + WebView"是**唯一正确解**——把 Go 核心用 gomobile 复用，密码学一份代码。若走 ExoPlayer 原生 DataSource，就得在 Kotlin 里重新实现 XSalsa20/AES-EME，这才真叫"手写密码学"，且容易和 rclone 格式跑偏。ExoPlayer 只作"WebView 体验不够"的兜底，且那时也必须复用同一份 Go 实现（cgo/JNI），不是重写。

## 7. 阶段 1 前的验证清单（先证明链路，再写 UI）

### 7.1 十分钟摸底（不改一行代码，用 OpenList 的 crypt 驱动）

1. OpenList 里加一个存储：类型选 `crypt`，包住目标云盘存储；密码先填测试值。
2. **目标存储必须开"Web 代理"**（否则底层只有 302 直链，一定拿不到 206）。
3. 用 WebDAV 客户端 PUT 一个 >=100 MB 的视频，然后：

```
curl -sI -u <user>:<pass> -H "Range: bytes=0-1023" \
     http://127.0.0.1:5244/dav/<路径>
```

判定：**返回 `206` + `Content-Range: bytes 0-1023/<size>`** 才算 Range 成立；返回 `200` 就是没走通，先解决这条再谈别的。

### 7.2 证明"能跳到 90%、不整包下载"

```
# 在 4 GB 文件 90% 位置读 2 MB，并打印实际发出的 HTTP Range 头
rclone cat --config <local.conf> --dump headers \
  "chunker:<vault>/media/<密文名>" --offset 3865470566 --count 2097152 > /dev/null
```

判定三条同时满足：耗时 < 3 s；日志里只有一个（或极少数）小段 `Range: bytes=...`；总下载量远小于文件大小。

### 7.3 云端侧"全是乱码"检查

- 云盘网页端/官方 App 打开目标目录：文件名全是 base32 乱码、无 `.jpg/.mp4` 后缀、无缩略图、点开无法预览。
- 下载其中一个：`file` 识别不出媒体类型；头部应为 `RCLONE\0\0` + 随机字节。

### 7.4 参数基线（先按这个起步再调）

```
--timeout 10m --contimeout 30s
--low-level-retries 10 --retries 3 --retries-sleep 30s
--transfers 2 --tpslimit 4
chunker: chunk_size=500Mi, name_format=*.rcc##（更短、更不像工具产物）
crypt:   filename_encryption=standard, directory_name_encryption=true,
         filename_encoding=base32, suffix=none
```

（`suffix=none` 去掉 `.bin`，云端文件名更干净；这会改变密文可见命名规则，**上线前定死，之后别改**。）

## 8. 需要你拍板的 3 个决策点

1. **运行时形态**：MVP 直接上"Go 内嵌 rclone + 自建网关"（B），还是先用子进程 `serve webdav`（A）跑通再迁？
   建议：**A 只做 7.1/7.2 摸底（今天就能出结论），正式代码直接写 B**——移动端阶段 4 只能靠 B。
2. **UI/外壳**：纯本地 Web（先浏览器打开）-> 后加 Wails/WebView2 壳；还是直接 Electron。
   建议：**Go 起 HTTP + 静态前端，先浏览器；壳最后加**。壳会拖慢 Range 链路调试，而阶段 1 唯一目标是证明 206。
3. **是否接受 rclone 的泄漏面**（确定性文件名、16 字节精度的文件大小、mtime）。
   建议：**接受**。想消掉这些就得自建容器格式 + 自写容器层密码学，直接违反"禁止自创密码学"，收益不匹配。

## 9. 交付边界

阶段 1 只证明一件事：**"导入一份密文 -> 列表页看到解密名 -> 点开播 -> 拖到 90% 位置 3 秒内起播 -> 抓包只有小段 Range"**。
相册墙、内置驱动、移动端，全部建立在这条链路之上；这条链路不成立，后面所有工作都是空中楼阁。
